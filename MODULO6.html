O núcleo fiscal: emissão de NF-e em massa

Por que a API v3 não gera NF a partir do pedido, como montar o documento fiscal inteiro, recálculo de vencimentos e os quatro estados possíveis de uma emissão.

6.1 A lição mais importante do projeto

# ❌ VALIDATION_ERROR: "A nota deve ter ao menos um item",
#    "Data de operação inválida", "Número do documento não informado"
await client.post("/nfe", json={"pedidoVenda": {"id": 12345}})
Fundamental

A API v3 do Bling não preenche a NF a partir do pedido. Isso funciona na interface web, não na API. O cliente precisa montar o documento fiscal inteiro.

O fluxo correto — 7 passos por pedido

1. GET /pedidos/vendas/{id} → dados do pedido 2. Validação local → falha rápida, sem gastar requisição 3. GET /contatos/{id} → CPF/CNPJ, IE, endereço completo 4. Montar payload → tipo, dataOperacao, contato, itens, parcelas, transporte 5. POST /nfe → NF "Em digitação" → nf_id 6. POST /nfe/{id}/enviar → transmite à SEFAZ → "Autorizada" 7. GET DANFE + XML → e-mail

Criar ≠ emitir. Após o passo 5 a NF existe, mas não tem validade fiscal.

6.2 Separação de responsabilidades

nf_service monta o payload — ele conhece a regra de negócio.
bling_client só faz HTTP — ele não sabe o que está enviando.

É por isso que routers/pedidos.py é tão fino:

relatorio = await nf_service.emitir_nfs_massa(
    db=db, usuario_id=usuario_id, pedido_ids=pedido_ids,

6.3 Validação prévia (falha rápida)

def _validar_pedido_basico(pedido: dict) -> str | None:
    contato = pedido.get("contato") or {}
    digitos = "".join(c for c in (contato.get("numeroDocumento") or "") if c.isdigit())

    if not digitos:
        return f"Cliente '{contato.get('nome','?')}' sem CPF/CNPJ cadastrado."
    if len(digitos) not in (11, 14):
        return (f"Cliente '{contato.get('nome','?')}': CPF/CNPJ inválido "
                f"({len(digitos)} dígitos — esperado 11 ou 14).")

    itens = pedido.get("itens") or []
    if not itens:
        return "Pedido sem itens — não é possível emitir NF."

    for item in itens:
        if float(item.get("valor") or 0) <= 0:
            desc = item.get("descricao") or item.get("codigo") or "?"
            return f"Item '{desc}' com valor zero — corrija o pedido no Bling."
    return None

Contrato: None = válido, str = motivo do erro — consistente com get_valid_access_token.

Cada validação local economiza 2 requisições ao Bling (respeitando o rate limit) e produz mensagem acionável em vez de um VALIDATION_ERROR genérico. "".join(c for c in cpf if c.isdigit()) normaliza 123.456.789-01 → 12345678901.

Evolução

Validar também os dígitos verificadores: o Bling rejeita 11111111111 (11 dígitos, mas inválido).

6.4 O padrão .get(x) or default

float(item.get("valor") or 0)

Por que não .get("valor", 0)? Porque a Bling pode retornar "valor": null. Com .get(k, 0) você recebe None (a chave existe!) e float(None) explode. O or trata None, "" e 0 de uma vez.

6.5 Montagem do payload — campo por campo

Data de operação (form → pedido → hoje)

if data_base:
    data_operacao = data_base.strip()[:10]
else:
    data_saida_raw = (pedido.get("dataSaida") or "").strip()
    if data_saida_raw and data_saida_raw != "0000-00-00":
        data_operacao = data_saida_raw[:10]
    else:
        data_operacao = datetime.now().strftime("%Y-%m-%d")

O [:10] corta "2026-08-11 00:00:00" → "2026-08-11". O teste != "0000-00-00" trata a zero date legada do MySQL do Bling.

Contato — o do pedido é resumido, o do cadastro tem IE e endereço

numero_doc = ((contato_completo.get("numeroDocumento") or "")
              or (contato_pedido.get("numeroDocumento") or "")).strip()

contato_nf = {
    "nome": (contato_completo.get("nome") or contato_pedido.get("nome") or "").strip(),
    "tipoPessoa": contato_completo.get("tipoPessoa") or contato_pedido.get("tipoPessoa") or "F",
    "numeroDocumento": numero_doc,
}
if ie := (contato_completo.get("ie") or "").strip():
    contato_nf["ie"] = ie   # só PJ; enviar vazio pode gerar rejeição
Padrão de campo opcional

Só inclua a chave se houver valor. Enviar "ie": "" costuma gerar rejeição na SEFAZ.

Truncamentos ([:60], [:8], [:2]) respeitam os limites do layout da NF-e. O CEP tem hífens removidos.

Itens

item_nf = {
    "codigo":     str(item.get("codigo") or ""),
    "descricao":  str(item.get("descricao") or "Produto"),
    "unidade":    str(item.get("unidade") or "UN"),
    "quantidade": float(item.get("quantidade") or 1),
    "valor":      float(item.get("valor") or 0),
}
if (aliq := float(item.get("aliquotaIPI") or 0)) > 0:
    item_nf["aliquotaIPI"] = aliq   # zero causa rejeição — omitir

Parcelas — recálculo de vencimento (a lógica mais sutil)

if data_base and data_saida_original and data_venc_str:
    dt_base_orig = datetime.strptime(data_saida_original, "%Y-%m-%d")
    dt_venc      = datetime.strptime(data_venc_str, "%Y-%m-%d")
    ddl = max(0, (dt_venc - dt_base_orig).days)      # dias de prazo
    data_venc_str = (dt_operacao + timedelta(days=ddl)).strftime("%Y-%m-%d")

Se o usuário emite com data retroativa, os vencimentos precisam acompanhar, preservando o prazo:

$$\text{DDL} = \text{venc}_{\text{original}} - \text{saída}_{\text{original}}$$

$$\text{venc}_{\text{novo}} = \text{data\_operação} + \text{DDL}$$

Exemplo: pedido de 01/08 com vencimento 31/08 (DDL = 30). Emitindo com data_base=05/08 → novo vencimento 04/09. Sem esse recálculo a parcela venceria antes da emissão.

max(0, ...) impede DDL negativo. O except ValueError: pass mantém a data original se o parse falhar — degradação graciosa.

# Fallback obrigatório: o Bling exige ao menos 1 parcela
if not parcelas_nf:
    total = float(pedido.get("total") or pedido.get("totalProdutos") or 0)
    parcelas_nf.append({"data": data_operacao, "valor": total})

Transporte

transporte_nf = {
    "fretePorConta": transporte_pedido.get("fretePorConta", 9),  # 9 = sem frete
    "volumes": [],   # obrigatório no schema, pode ser vazio
}

Códigos: 0 remetente (CIF), 1 destinatário (FOB), 9 sem frete. A etiqueta é o endereço impresso no DANFE.

O truque das observações — evitando XML duplicado

observacoes_finais = f"Pedido Original: {pedido_id}"
if observacoes:
    observacoes_finais = f"{observacoes} | {observacoes_finais}"
payload["observacoes"] = observacoes_finais
Bug real resolvido

O Bling rejeita com “Já existe uma nota fiscal com este XML” quando dois pedidos geram documentos idênticos (mesmo cliente, mesmos itens, mesma data). Injetar o pedido_id nas observações garante unicidade e rastreabilidade.

payload = {
    "tipo": 1,                     # NF-e de saída

6.6 Orquestração best-effort

O laço principal usa continue em cada falha — um pedido ruim nunca interrompe os demais. Se o usuário seleciona 20 pedidos e o nº 7 está sem CPF, os outros 19 são emitidos.

Cada erro é registrado em dois lugares: relatorio["erros"] (tela imediata) e operacoes_nf (auditoria permanente).

async def _salvar_operacao(db, usuario_id, pedido_id, nf_id, status, erro, email):
    db.add(OperacaoNF(usuario_id=usuario_id, pedido_id_bling=pedido_id,
                      nf_id_bling=nf_id, status=status,
                      erro_descricao=erro, email_enviado=email))
    await db.commit()   # commit por operação
NF (aqui)Produtos (M7)
EstratégiaCommit por operaçãoCommit único no fim
JustificativaDocumento fiscal é irreversível; perder o registro é gravePreço é reversível; atomicidade vale mais

Se o processo cair no pedido 15, os 14 anteriores já estão persistidos. Trade-off consciente: mais I/O em troca de durabilidade.

6.7 Rate limiting e assincronia da SEFAZ

nf_data = await bling_client.criar_nf(access_token, payload_nf)
await asyncio.sleep(3)      # respeita rate limit do Bling
...
await asyncio.sleep(5)      # dá tempo ao Bling de processar a criação
await bling_client.enviar_nf(access_token, nf_id)

asyncio.sleep (não time.sleep) libera o event loop para outras requisições. Custo: ~8 s por pedido. 20 pedidos ≈ 3 minutos de requisição HTTP — motivo para a solução do Módulo 8.

6.9 Bug a corrigir — diagnóstico em produção

# ❌ dentro de nf_service.emitir_nfs_massa
await bling_client.descobrir_ids_situacoes_venda(access_token)

Isso executa a cada emissão em massa: gasta uma requisição do rate limit, imprime no stdout e não tem tratamento de erro. Remova e coloque num script:

# scripts/descobrir_situacoes.py — rodar UMA vez
import asyncio
from db.database import AsyncSessionLocal
from services import bling_client, token_service

async def main(usuario_id: int):
    async with AsyncSessionLocal() as db:
        token = await token_service.get_valid_access_token(db, usuario_id)
        await bling_client.descobrir_ids_situacoes_venda(token)

asyncio.run(main(1))

6.10 Pós-emissão: marcar o pedido como faturado

try:
    await bling_client.atualizar_situacao_pedido(access_token, pedido_id, 9)
except Exception as exc:
    logger.warning("Não foi possível atualizar situação do pedido %s: %s", pedido_id, exc)

Dentro de try/except sem continue: a NF já foi emitida com sucesso. Falhar aqui é cosmético — o pedido só continua aparecendo na listagem idSituacao=6. Confirme que 9 = “Faturado” na sua conta usando o script da seção 6.9.

6.11 E-mail único com todos os anexos

if relatorio["sucesso"]:
    try:
        await email_service.enviar_email_nfs(email_destino, anexos)
    except Exception as exc:
        relatorio["aviso_email"] = (
            f"NFs emitidas com sucesso, mas falha no envio do e-mail: {exc}. "
            "Os documentos podem ser baixados manualmente no Bling."
        )

Um e-mail para N notas (não N e-mails). Falha de SMTP nunca invalida a emissão fiscal — vira aviso_email, não erro. Separação correta entre o essencial (fiscal) e o acessório (notificação).

Risco de memória

anexos acumula todos os PDFs + XMLs em RAM. Com 100 notas × ~250 KB ≈ 25 MB por requisição. Para volumes maiores, grave em disco/S3 e envie links.
