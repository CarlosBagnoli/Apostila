Produtos, preços e o problema das variações

Reajuste percentual em massa, o bug do PUT com grade incompleta, herança de preço e resiliência por item.

7.1 A regra de negócio

Aplicar um percentual a todos os produtos de uma categoria:

$$P_{\text{novo}} = \text{round}\left(P_{\text{antigo}} \times \left(1 + \frac{p}{100}\right),\ 2\right)$$

preco_novo = round(preco_anterior * (1 + percentual / 100), 2)
Por que arredondar?

Ponto flutuante IEEE-754 não representa decimais exatamente: 10.5 * 1.1 = 11.549999999999999. Sem round, o Bling receberia um preço com 15 casas decimais.

Para produção

Use Decimal com ROUND_HALF_UP — é o padrão contábil brasileiro:

from decimal import Decimal, ROUND_HALF_UP
novo = (Decimal(str(preco)) * (1 + Decimal(str(pct)) / 100)) \
       .quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)

7.2 O bug das variações

GET /produtos retorna variações incompletas (sem preço). Como o PUT /produtos/{id} exige o array completo, enviar o objeto da listagem provoca 400 Bad Request.

tem_variacoes = bool(produto.get("variacoes"))

if tem_variacoes:
    # Busca o detalhe individual para obter variações com preço
    produto_completo = await bling_client.get_produto_detalhe(access_token, produto["id"])
    payload = _aplicar_percentual_com_variacoes(produto_completo, percentual)

    # Atualiza o relatório com o preço do detalhe (mais preciso)
    preco_anterior = float(produto_completo.get("preco") or preco_anterior)
    preco_novo = round(preco_anterior * (1 + percentual / 100), 2)
    entrada.update({"preco_anterior": preco_anterior, "preco_novo": preco_novo})
else:
    payload = {**produto, "preco": preco_novo}   # PUT simples
O detalhe crítico do spread

{**produto, "preco": novo} copia todos os campos originais e sobrescreve só preco. Fundamental porque o PUT da Bling é substituição total, não patch. Enviar apenas {"preco": X} apagaria nome, código, estoque e tributação do produto.

É por isso que o schema BlingProduto serve só para leitura: ele mapeia ~6 campos, o produto real tem dezenas.

7.3 Herança de preço nas variações

def _aplicar_percentual_com_variacoes(produto: dict, percentual: float) -> dict:
    """
    Aplica o percentual ao produto pai e a cada variação que tem preço próprio.
    Variações com preco=0 herdam o preço do pai no Bling — não alteramos o campo
    delas para não sobrescrever a herança.
    O array 'variacoes' COMPLETO é obrigatório no PUT de produtos com grade.
    """
    preco_pai      = float(produto.get("preco") or 0)
    novo_preco_pai = round(preco_pai * (1 + percentual / 100), 2)

    novas_variacoes: list[dict] = []
    for variacao in produto.get("variacoes") or []:
        preco_var = float(variacao.get("preco") or 0)
        if preco_var > 0:
            # Variação tem preço individual — aplica o mesmo percentual
            novas_variacoes.append({**variacao,
                                    "preco": round(preco_var * (1 + percentual/100), 2)})
        else:
            # Variação herda do pai — mantém como está, Bling gerencia internamente
            novas_variacoes.append(variacao)

    return {**produto, "preco": novo_preco_pai, "variacoes": novas_variacoes}
Regra crítica

preco = 0 numa variação significa herança (“Utilizar informações do produto pai”), não “de graça”. Alterar esse campo desligaria a herança e congelaria o preço — quebrando o comportamento esperado pelo lojista. Preservar o 0 é a decisão correta.

    entrada = {

    }

    try:
        ...
        await bling_client.atualizar_produto(access_token, produto["id"], payload)
        resultados.append(entrada)
        db.add(AtualizacaoPreco(

            preco_anterior   = preco_anterior,
            preco_novo       = preco_novo,
        ))
    except Exception as exc:
        # Falha isolada — registra e segue para o próximo produto (antes era 500)
        logger.error("Falha ao atualizar '%s': %s", produto.get("nome"), exc)
        erros.append(entrada)

if resultados:
    await db.commit()     # commit único no final

O entrada é construído antes do try e reutilizado nos dois caminhos — evita duplicação e garante que o relatório de erros também mostre os preços tentados. O if resultados: evita um commit vazio quando tudo falha.

7.6 Débitos técnicos

  • Sem paginação: limite=100 em get_produtos. Categorias com mais de 100 itens são silenciosamente truncadas → solução no M8.
  • Sem rate limit no loop: ao contrário do nf_service, não há asyncio.sleep. Com 100 produtos você pode estourar o limite do Bling. Adicione await asyncio.sleep(0.5).
  • Sem confirmação: POST /produtos/atualizar altera preços irreversivelmente sem dry-run. Sugestão: checkbox “apenas simular”.
